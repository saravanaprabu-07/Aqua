# AquaTrend
### Groundwater Level Forecasting & Depletion Trend Platform
*Level 1 ML Hackathon Project*

## Problem Statement
Groundwater levels are influenced by rainfall, extraction, recharge, soil characteristics,
temperature and seasonal patterns. This project builds an ML platform that estimates future
groundwater levels, identifies locations with persistent decline, distinguishes historical
measurements from forecast values, provides seasonal analysis, and enables comparison between
regions — converting predictions into decision-support information for groundwater monitoring.

## Proposed Solution
**AquaTrend** is a Streamlit dashboard backed by a Random Forest time-series forecasting model
and an explainable trend-classification module, built on real Central Ground Water Board (CGWB)
monitoring data for India. It provides:
- Historical vs. ML-forecast groundwater visualization per district
- Data-driven depletion trend classification (Improving / Stable / Mild Decline / Significant
  Decline) with a persistent-decline flag
- Seasonal groundwater analysis
- Multi-region comparison
- Monitoring-priority decision support

## Dataset
- **60 Indian districts**, quarterly readings, **May 1996 – Jan 2017** (84 quarters)
- 4,982 district-quarter records, built by aggregating readings from thousands of individual
  CGWB monitoring wells
- Core variable: **Depth to Water Level (metres below ground level)**. A larger value means
  the water table is deeper (groundwater has declined); a smaller value means it is closer to
  the surface (groundwater is healthier).
- No missing values in the final processed file (see `dataset_source.txt` for exact cleaning
  steps applied to the raw CGWB extract).

## Dataset Source
Original data: **Central Ground Water Board (CGWB), Government of India**
Public repository used to obtain it: https://github.com/craigdsouza/cgwb
(`data/CGWB_data_wide.csv`, compiled by Tejasvi Hora, University of Waterloo, from official
CGWB records)

Full provenance and processing steps: see [`dataset_source.txt`](dataset_source.txt).

Rainfall, extraction and soil data were **not available** in this source and were **not
fabricated** — per the hackathon rules, the model instead relies on genuine groundwater
time-series features (lags, rolling averages, seasonal/date features).

## Features
| Feature | Why it's used |
|---|---|
| `lag_1`, `lag_2`, `lag_4` | Depth value 1 / 2 / 4 quarters ago (≈3mo/6mo/1yr) — recent and same-season history |
| `rolling_avg_4` | Trailing 4-quarter (1-year) average — smooths short-term noise |
| `quarter_index` | Sequential time counter per location — captures long-term trend |
| `year`, `month`, `season` | Calendar/seasonal position (Winter/Summer/Monsoon/Post-Monsoon) |
| `location` (one-hot) | District identity — different districts have different baselines |
| `num_wells_reporting` | Number of CGWB wells behind a reading — a data-confidence signal |

*(Lags are expressed in quarters, not months, because the source data itself is quarterly —
adapted from the hackathon's suggested monthly Lag‑1/3/6/12 to the real granularity of this
dataset.)*

## ML Algorithm
**Random Forest Regressor** (scikit-learn). Chosen because it captures non-linear relationships
between lag/seasonal features and the target, is robust to the noise typical of manual well
readings, and is straightforward to explain to non-technical judges: *"it grows many decision
trees on the lag and seasonal features and averages their predictions."*

## Data Preprocessing
1. Parse dates, remove duplicate rows
2. Drop rows with missing target values
3. Remove physically impossible outliers (negative depth, or depth > 50 m — a documented,
   justified cutoff, not an arbitrary one)
4. Sort chronologically within each location
5. Engineer calendar features (year, month, season) and a per-location quarter index
6. Engineer lag features (`lag_1`, `lag_2`, `lag_4`) and a rolling average (`rolling_avg_4`)

See `src/preprocessing.py` for the full, commented pipeline.

## Model Training
- **Train/Test split: strictly chronological, never random.** For every location, the most
  recent 8 quarters (2 years) are held out as the test set; everything earlier is used for
  training. This mirrors the real forecasting task (predict the future from the past) and
  avoids information leakage.
- Train size: 4,262 rows · Test size: 480 rows

## Evaluation Metrics
*(actual values generated by this project's own run — see `results/model_results.csv` and the
executed notebook for the full output; these are not invented numbers)*

| Metric | Value |
|---|---|
| MAE  | 0.490 m |
| RMSE | 0.679 m |
| R²   | 0.906 |

On average, the model's one-quarter-ahead depth prediction is within about half a metre of the
actual measured depth, and explains ~91% of the variance in the held-out chronological test set.

## Forecasting
Forecasting beyond one quarter uses a **recursive** approach: the model predicts the next
quarter, that prediction is fed back in as the newest lag value, and the process repeats for as
many future quarters as requested (1–8 in the dashboard). Historical (actual) and forecast
(predicted) values are always plotted with clearly different line styles/colors, and the chart
marks exactly where history ends and the forecast begins.

## Trend Analysis
For each location, a linear regression slope of depth-to-water-level vs. time is fit over its
full history. **Positive slope = water table getting deeper = decline.** Classification
thresholds are **data-driven**, computed from the mean and standard deviation of the slope
values actually observed across the 60 locations in this dataset:

- **Improving**: slope < 0
- **Stable**: 0 ≤ slope < mean slope (≈0.0366 m/quarter)
- **Mild Decline**: mean ≤ slope < mean + 1 std dev (≈0.0366 to ≈0.1009 m/quarter)
- **Significant Decline**: slope ≥ mean + 1 std dev

A location is additionally flagged **Persistent Decline** if depth worsened in at least 75% of
its last 8 quarter-over-quarter changes. Result on this dataset: 10 Improving, 33 Stable,
11 Mild Decline, 6 Significant Decline — with Punjab districts (Sangrur, Patiala, Ludhiana,
Jalandhar, Moga, Bathinda) dominating the "Significant Decline / High Priority" list, consistent
with widely reported groundwater stress in that region.

## Dashboard
Built with **Streamlit**, six sections:
1. **Overview** — totals, date range, declining-location count, trend distribution
2. **Groundwater Forecast** — location selector, historical vs. forecast chart, forecast table
3. **Depletion Trend** — category, slope, persistent-decline flags, full trend table
4. **Seasonal Analysis** — average depth by season/month
5. **Region Comparison** — multi-select comparison chart and table
6. **Dataset & Model** — source, features, methodology, evaluation metrics

## How to Run
```bash
pip install -r requirements.txt
streamlit run app.py
```
The dashboard will open in your browser (default: http://localhost:8501).

To re-run the full ML workflow standalone:
```bash
cd AquaTrend
python src/model.py            # trains model, prints metrics, saves results/model_results.csv
python src/trend_analysis.py   # runs trend analysis, saves results/trend_analysis.csv
jupyter notebook notebooks/groundwater_analysis.ipynb   # full step-by-step notebook
```

## Limitations & Future Scope
- Rainfall, extraction and soil data were unavailable in the source and were not fabricated;
  incorporating IMD rainfall data would likely improve accuracy further.
- The current dataset ends in January 2017; adding more recent CGWB readings would let the
  model forecast closer to the present day.
- Well-level (rather than district-averaged) forecasting could give finer-grained warnings.
